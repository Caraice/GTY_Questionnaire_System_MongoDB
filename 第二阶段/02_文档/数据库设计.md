# 数据库设计

版本0.11.0，MongoDB原生驱动PyMongo；所有账号、会话、问卷、答卷与内部持久配置均保存在MongoDB。

## 集合划分

| 集合 | 文档粒度 | 关键字段 | 嵌入或引用的理由 |
| --- | --- | --- | --- |
| users | 一个账号 | _id、username、password_hash、created_at、schema_version | 用户独立生命周期，不把账户信息复制到问卷 |
| sessions | 一次登录 | user_id、token_hash、created_at、expires_at | 可注销、过期；引用用户 ID；TTL 回收 |
| app_settings | 一项内部配置 | _id、schema_version、secret | 保存 HMAC 持久密钥，与业务答卷分离，跨重启稳定且不由 API 暴露 |
| surveys | 一份问卷定义 | owner_id、share_id、title、description、status、deadline、allow_anonymous、allow_multiple、questions、rules、version、published_version、schema_version | 题目和规则随问卷读取，嵌入便于原子更新；当前最多 200 题为实现边界，非教师要求 |
| responses | 一次有效提交 | survey_id、survey_version、respondent_key、respondent_id、anonymous、answers、path、attempt_key、submission_key、request_hash、submitted_at | 答卷持续增长，独立集合支持并发插入；原始请求指纹用于幂等核对 |

不把所有数据装进一个集合，也不按“每种题型一张表”机械复制关系数据库设计。不同题型在问卷内有不同的嵌套 validation，适合文档建模。用户和答卷使用引用是控制冗余的取舍，不表示 MongoDB 禁止引用或关系数据库无法实现问卷。使用 MongoDB 首先是课程硬要求，其次是该模型与可变题型结构相适应。

## 问卷定义示意

```json
{
  "_id": "survey-uuid", "schema_version": 1, "version": 1,
  "owner_id": "user-uuid", "share_id": "random-share-id",
  "title": "校园调查", "description": "示例",
  "status": "draft", "deadline": null,
  "allow_anonymous": true, "allow_multiple": false,
  "questions": [
    {"id":"q1","type":"single","title":"是否在校","required":true,
     "options":[{"id":"yes","label":"是"},{"id":"no","label":"否"}],"validation":{}},
    {"id":"q2","type":"number","title":"年龄","required":true,
     "validation":{"minimum":0,"maximum":120,"integer_only":true}}
  ],
  "rules": [{"source_question_id":"q1","operator":"eq","value":"no","target_question_id":"END"}]
}
```

示意省略创建、更新时间；实际 MongoDB 保存 BSON Date，统一 UTC，API 返回带时区 ISO 时间，页面转换显示。题目 ID 和选项 ID 稳定，不能用数组下标作为持久 ID。题目顺序由 questions 数组决定。跳转目标和答案使用这些稳定 ID。

## 索引与一致性

| 集合 | 索引 | 作用 |
| --- | --- | --- |
| users | username 唯一 | 小写标准化后避免重名，依靠唯一索引防并发注册冲突 |
| sessions | token_hash 唯一；expires_at TTL | 会话查询和回收；API 另检查过期时间，不能依赖 TTL 及时删除 |
| surveys | share_id 唯一；owner_id + created_at | 分享链接定位；按所有者列出问卷 |
| responses | survey_id + submitted_at | 整卷统计与时间检索 |
| responses | survey_id + survey_version + submitted_at + _id | 同冻结内容版本统计和内容列表稳定排序 |
| responses | survey_id + respondent_key + attempt_key 唯一 | 不允许重复时 attempt_key=once，原子防止并发重复；允许时取本次提交键 |
| responses | survey_id + respondent_key + submission_key 唯一 | 请求重试幂等，避免同一次提交重复记数 |

当前 schema.py 建立这些索引，0.6.0 已接入实际写入策略并完成真实并发与重试测试。准入写入会串行修改问卷的一项内部序号，不把该序号当提交总数，也未声称无写热点或已完成压力测试。

数据库 validator 检查基础字段、类型与状态；Pydantic 检查接口结构、配置边界和唯一题号。JumpRule 的题型适配、引用和前向顺序由已实现的规则定义校验检查；domain/routing已负责执行和路径重建。答案合法性需要服务端业务校验，不能只靠 schema。

## 答卷和匿名策略

非匿名保存 respondent_id；匿名置空，创建者统计不返回身份。使用 app_settings.response_hmac 的持久密钥按带分隔的 survey_id 与 user_id 计算 HMAC respondent_key，匿名切换保持同一问卷内标识，防止绕过重复限制。密钥原子 setOnInsert、跨重启保持，应随数据库备份且不随意轮换；不由 API 返回。此方案面向创建者匿名，数据库管理员仍可能关联，不宣称绝对匿名。

答案以题号到值的对象保存；单选存选项 ID，多选存校验无重复的选项 ID 数组（不静默去重），文本裁剪首尾空白，数字保留原始有效数值。path 来自服务端重建，禁止客户端指定；未知或路径外答案拒绝。遗漏不写答案对象，路径仍包含访问过的可选题。统计只使用同问卷同冻结版本的已保存答卷，跳过/空值不进入单题分母，0计入。独立聚合测试仍预置样本，另有真实 POST 到保存再聚合的端到端测试。

## 状态和内容版本

已实现状态：draft → published → closed。发布前重新验证所有题目、规则及期限，published/closed 的题目与规则冻结。超过 deadline 后状态仍可为 published，但派生 availability 为 expired；填写和提交每次重新读库并检查当前 UTC 时间，deadline <= now 时拒绝。过期 published 可通过未来期限或取消期限恢复访问；手动 closed 不可重新开放。

题目、规则、发布、关闭和期限更新都使用 `expected_version` 乐观锁：按 `_id + owner_id + status + version` 原子更新对应字段、updated_at 并递增 version。预检查用于友好报错，条件写入才是并发保证；发布与修改题目、关闭与改期限的竞争均有真实 MongoDB 测试。规则保存、执行与路径重建均已实现；准入内部序号不递增管理版本。

version 现为管理修订号。新增可选 published_version 在发布时等于发布后的 version，表示冻结的内容版本；后续期限/关闭只递增管理版本，published_version 不变。旧已发布文档若没有该字段，读取回退到现有 version，首次管理写入补写该基线；不清空旧集合，不替换 validator，不需破坏性迁移。schema_version 仍表示文档结构代际。

0.6.0 提交保存已实现。最终准入点为 surveys 上条件原子写入 submission_sequence，匹配 published、冻结版本及应用/数据库时钟下未到期；不改管理 version。先准入的请求可在关闭后完成 responses 插入；关闭/期限变更先发生则拒绝。两集合不是事务，准入序号可能有空洞；统计只聚合真实答卷。插入或确认失败返回503，原键重试恢复；同请求已保存的回执可在关闭/到期后重放，不新增。

## 第二阶段如何从原结构扩展

## 为什么保留问卷内的题目

第一阶段的questions数组同时承担题目展示、题序、跳转和解释旧答案的作用。数组内的id已经被rules、answers和path引用，不能把它改成题库的全局ID，也不能让已发布问卷自动读取题库“最新版本”。

本轮保留原问卷快照，使用独立的question_usages集合保存来源关系。迁移不向questions塞入新字段，避免现有Pydantic输入契约和前端保存丢字段；surveys、responses、users、sessions和app_settings均不执行更新。旧的schema_version、version、published_version及原validator和索引也不改。

这仍是MongoDB文档建模：问卷保留一起读取和冻结的嵌入快照；共享题目身份、历史版本和反向引用具有独立生命周期，放在独立集合中。没有按题型机械拆表，也没有用清库重建解决兼容问题。

## 三种 ID 分清楚

| 标识 | 表示什么 | 变化规则 |
| --- | --- | --- |
| template_id | 同一道独立题目 | 保存新版本、恢复时不变；另存为新题时新建 |
| template_version_id | 一次固定内容快照 | 每次版本保存和恢复都新建，原记录不覆盖 |
| question.id / instance_id | 题目在某份问卷中的一次出现 | 每次导入新建，排序及主动升级时保持 |

选择题选项 ID 在版本内容中保留，答案与跳转先按实例 ID 定位，再解释该实例的选项 ID。因此两道重复导入题即使有同名、同 ID 的选项，也不会把回答或规则合并。统计页的标题与筛选补上问卷内题号，方便区分相同题干。

## 集合、字段和索引

沿用 M1 的 question_templates、question_versions、question_usages、schema_migrations。本轮增加的 validator 和索引在 `database/bank_schema.py`；原有 `database/schema.py` 不替换、不清库。

| 集合/字段 | 职责 | 主要索引 |
| --- | --- | --- |
| question_templates | 所有者、当前头版本、edit_version；保存中断时暂存 pending_version | owner_id + updated_at；旧迁移来源唯一索引 |
| question_versions | 不可变内容、版本号、content_hash、parent/derived/restored 来源及操作类型 | template_id + number 唯一；parent、derived 查询索引 |
| question_banks | 题库名称和所有者 | owner_id + created_at |
| question_bank_memberships | 题库与题目的多对多关系，不存题目内容或固定版本 | bank_id + template_id 唯一；反向 template_id + bank_id |
| question_grants | 指定版本给指定账号的使用权限；active、revision、准入次数 | version_id + grantee_id 唯一；grantee_id + active + template_id |
| surveys.question_sources[] | 在线导入的实例、来源题目、来源版本、版本号、原始/归一化摘要和本地修改标记 | 版本引用多键索引；owner_id + 来源题目多键索引 |
| question_usages | M1 迁移时的历史引用关系 | survey_id + instance_id 唯一；按题目/版本查询 |

题库成员关系与内容版本分开：修改归属不会生成内容版本，新增版本不会修改题库成员关系。另存产生新的题目身份，而不是把原题改名。

在线引用放在问卷顶层的独立数组，题干、选项仍使用原 Question 模型，没有往旧题型输入中塞来源字段。这样在单机 MongoDB 上，题目副本、引用来源、排序和问卷 version 能在一个条件写入中一起提交，避免问卷落库而独立引用关系缺失。读取时兼容合并 M1 的 question_usages；显式更新旧引用后，以问卷内的新来源为准，旧迁移记录留存。引用查询只统计仍在问卷中的实例。

## 旧问卷迁移及兼容

## 本轮实际新增的集合与字段

可执行定义在 [database/library_schema.py](../01_可运行代码/database/library_schema.py)。新命名空间的schema_version也从1开始，迁移编号002不等于把旧文档schema_version改为2。

| 集合 | 核心字段 | 本轮写入方式 |
| --- | --- | --- |
| question_templates | _id、owner_id、latest_version_id、edit_version、visibility、origin、created_at、updated_at | 每个旧题实例创建一个私有题目；首次edit_version=1，latest_version_id指向v1 |
| question_versions | _id、template_id、number、parent_version_id、derived_from_version_id、restored_from_version_id、content、content_hash、created_by、created_at、origin | 创建number=1的内容快照；三个来源字段为null；不覆盖已有内容 |
| question_usages | _id、survey_id、instance_id、template_id、template_version_id、content_hash、source_survey_version、created_at、origin | 记录原实例对应的独立题目和固定版本，不改原题号 |
| schema_migrations | _id、number、completed_at、initial_surveys、initial_questions | 仅全部完成后插入一次完成标记；重复运行仍会重新检查来源，不以标记跳过核对 |

content复制原题目中除局部id外的全部字段，包括选项id、选项顺序、必答、题型和限制。迁移只验证原题目，不使用model_dump覆盖原数据，因此不会补默认字段、裁剪旧文字或转换原数值类型。content_hash使用规范扩展JSON计算，能区分布尔、整数、浮点和数组顺序。

新记录的created_at表示本轮采集入库时间，不拿原问卷的创建时间冒充题目创建时间。owner_id继承原问卷所有者；旧结构没有可靠的题目原创作者，所以迁移的created_by为null，后续真正新建版本时再记录实际操作者。重复执行保留第一次入库时间，不重写已有审计字段。

source_survey_version仅记录首次捕获时的发布内容版本，旧问卷没有published_version时使用原version；它是来源审计信息，不替代答卷内的survey_version，也不代表草稿以后不能编辑。引用、导入和更新均须核对content_hash；草稿改动导致来源与已建快照不一致时，本迁移明确报冲突，不擅自覆盖v1或推断用户想创建新版本。

edit_version用于当前题目管理的乐观锁；number表示内容版本序号，二者不能混用。latest_version_id在新增版本或恢复时推进，迁移重跑不会把它重置成v1。当前迁移采用只插入、读取核对的方式保留内容；MongoDB管理员仍能直接改库，不声称validator能在数据库层独立实现内容不可修改。

## 怎样执行

在survey-system目录执行。命令必须显式指定目标库，连接默认读取MONGODB_URI；省略--apply时只读预检，不创建集合或索引。

```powershell
# 先启动MongoDB并设置实际连接；27019是第一阶段默认端口
$env:MONGODB_URI = 'mongodb://127.0.0.1:27019'

# 先在备份恢复出的隔离库演练
.\.venv\Scripts\python.exe -B -X utf8 -m scripts.migrate_question_library --database survey_stage1_copy
.\.venv\Scripts\python.exe -B -X utf8 -m scripts.migrate_question_library --database survey_stage1_copy --apply
# 再执行一次，应不再创建独立题目、版本和引用记录
.\.venv\Scripts\python.exe -B -X utf8 -m scripts.migrate_question_library --database survey_stage1_copy --apply
```

目标库名必须换成自己真实的备份演练库；空库成功不能证明原数据迁移通过。正式执行前备份业务库，暂停题目编辑、发布、关闭和期限变更，再对正式库按同样顺序预检与apply。启动网页和scripts.init_db不会自动执行002迁移。

命令输出JSON，包含mode、surveys、questions、pending、created、status和legacy_documents_rewritten。首次apply会创建记录，原样重跑的created应全为0，legacy_documents_rewritten始终为0。退出码0表示成功，2表示输入/来源/内容/结构冲突，1表示MongoDB操作失败。连接错误不回显可能带凭证的URI。

## 重跑、冲突与回退

ID由固定命名空间和来源生成，数据库依赖唯一索引防重；迁移写入仅使用setOnInsert，不用replace或set覆盖已有版本。先完整预检，再创建新结构和记录，执行前后均核对源问卷指纹。新问卷在首次迁移完成之后加入，也会在下次运行被发现。

单机MongoDB的这些写入不构成跨集合事务。中断时可能留下一部分新记录，但原问卷与答卷不受影响；修复连接后重跑会核对并补齐缺少记录。迁移期间若源定义变化，会返回失败，完成标记不代表已通过本次检查。停止修改后先预检；若已有快照与新源内容冲突，需要核对原因并由明确的后续迁移处理，不能靠自动覆盖、清库或按标题合并来消除冲突。

迁移本身不改写原问卷与答卷；当前题库功能使用新增集合。若回退第一阶段程序，应保留新增集合供核对，并核查第二阶段新数据的可读性，不能承诺无条件降级。本项目不提供一键删集合回滚，也未验证过正式业务库备份恢复。完成标记仅保留第一次成功的时间和数量，每次执行的实际数量以当次JSON报告为准。

## 权限和来源为什么这样处理

目前项目的问卷结果查看权限仍是问卷所有者。题目所有者能查看自己的题目定义，但不因此获得其他发布者的答卷；共享接收者也只能统计自己有权查看结果的问卷。两个方向都不开放对方的结果。Repository聚合开头再次带 `owner_id`，不是先查全库再由页面隐藏。

统计从 `surveys.question_sources` 读取在线引用，兼容 `question_usages` 中的旧迁移引用；实际答案键仍是问卷内实例ID。同题多次导入不会混掉题号。来源指纹、不可变版本原始指纹、问卷内归一化内容都要一致，不能只相信 `modified=false`。本地改写后的回答不冒充原版本，问卷本身的统计仍照常保留。

撤销共享后不能新导入，但已经导入自己问卷的内容和结果仍可统计。此时仅开放本人问卷实际引用的版本，来源历史入口按当前源题权限隐藏。版本定义损坏时显示原因，不伪装成正常的零回答统计。
